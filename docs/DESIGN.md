# Design: zero-data Geometry Dash RL

## Goal

Train an agent from random weights with no demonstrations, no pretrained visual encoder, no obstacle coordinates, and no pre-collected gameplay dataset.

The only learning loop is:

1. capture live pixels from the Geometry Dash window;
2. choose an action;
3. observe the next pixels;
4. receive a reward generated by the environment;
5. update the policy from the experience the agent generated itself.

## Baseline

The first baseline is Recurrent PPO from `sb3-contrib` using `CnnLstmPolicy`.

Observation:
- live client-area pixels;
- resized to 84x84;
- grayscale by default;
- no handcrafted game-state features.

Action space:
- 0: release the configured jump key;
- 1: hold the configured jump key.

The hold/release formulation is deliberate. It works for simple cube jumps and preserves the ability to learn duration-sensitive controls later.

Reward:
- small positive reward every live step;
- terminal penalty when a likely end-of-run screen is detected.

This does not tell the agent what a spike, platform, player, or safe jump is. It only says that remaining alive longer is preferable.

## Episode termination

There is no game-memory reading in the baseline. The environment uses visual motion only.

During normal play, Geometry Dash continuously scrolls. After a crash, the screen normally becomes nearly static. `MotionEndDetector` measures normalized frame-to-frame pixel change and ends the episode after several consecutive low-motion observations.

This is intentionally simple and label-free. The detector parameters are configurable because display resolution, game effects, FPS, and window mode can change the observed motion.

## Why Recurrent PPO first

A single frame does not directly expose velocity. The LSTM can infer temporal information from a sequence of observations. PPO also works naturally with experience gathered online and does not require a prebuilt replay dataset.

PPO's rollout buffer is generated automatically while the agent plays. It is training data, but it is not prior data: every transition is produced by the current agent during the current run.

## What is logged

`runs/episodes.csv` records:
- episode index;
- episode length;
- survival time;
- return;
- best survival time so far;
- termination reason;
- final visual-motion score.

TensorBoard logs optimization metrics. Model checkpoints are written under `models/`.

Raw frames are not persisted by default because long runs can create tens or hundreds of gigabytes. They are still consumed online by the policy and rollout buffer.

## Important first-run condition

Before starting `python -m gd_ai.train`, open the target level and leave the game on a state where pressing the configured start key begins/retries the same level. The environment then owns that key and restarts every episode automatically.

The AI itself still starts from zero. This initial UI positioning is only environment setup, not a demonstration or training example.

## Calibration

Run:

```powershell
python -m gd_ai.calibrate
```

It verifies:
- the correct game window is found;
- the client area can be captured;
- an image is saved to `runs/calibration.png`;
- frame-motion statistics are measurable.

For an active run, median motion should be clearly above `environment.freeze_motion_threshold`. On the retry/death screen it should normally be below that threshold. If not, adjust the threshold or the number of freeze frames.

Optional input test:

```powershell
python -m gd_ai.calibrate --test-input
```

## Training

Fresh random initialization:

```powershell
python -m gd_ai.train
```

Short validation run:

```powershell
python -m gd_ai.train --timesteps 20000
```

Resume a saved policy:

```powershell
python -m gd_ai.train --resume models/checkpoints/gd_agent_100000_steps.zip
```

Watch TensorBoard:

```powershell
tensorboard --logdir runs/tensorboard
```

## Evaluation

```powershell
python -m gd_ai.evaluate models/best_model.zip --episodes 10
```

Evaluation uses deterministic actions and performs no learning.

## Planned comparison track

After the live baseline is validated, the same environment can support controlled comparisons:

- Recurrent PPO: current baseline.
- DQN/Rainbow-style replay learning: useful for the discrete action space.
- Neuroevolution/NEAT: population-based learning from random networks.
- Model-based RL/Dreamer-style agents: learn a latent world model from self-generated experience.
- Multi-level training: determine whether the agent learned the game or only memorized one level.

The crucial research metric is generalization to levels that were not used during training.
